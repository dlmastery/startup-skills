# Deep Dives — The 8 Tier-1 Systems Behind Ascent's Mechanisms

Each dive: **Goal → Algorithmic approach → Inputs/outputs → Key design choice → Failure modes & fallbacks.** Status labels are strict: **[EXISTS]** = implemented in the PoC repo (`generalized_ml_autoresearch/`, file named); **[PARTIAL]** = implemented in reduced form; **[ROADMAP]** = specified here, not built. Source tags resolve in `research/sources.md`. PoC behavior is founder-reported (A6).

## 1. Composite fingerprint metric + SHA-256 keep/discard **[EXISTS: fingerprint + per-row logging · ROADMAP: automatic refusal on mismatch]**

- **Goal:** answer, tamper-evidently, the only question the loop asks 265 times in a row: *did this experiment strictly improve the thing we agreed to measure?*
- **Algorithmic approach — what exists:** a task-tailored scalar composite — default formula `min(val_primary, test_primary) − λ · n_below_threshold_folds` (`core/evaluation/composite.py`), pluggable via a small expression DSL or callable path. `fingerprint()` returns a SHA-256 digest of the formula config, and the runner logs `composite_fingerprint` on **every** experiment row (`core/runner.py:453`). That yields **tamper-evidence**: a mid-run formula rewrite changes the fingerprint on every subsequent ledger row, so any rewrite is permanently visible in the append-only ledger and detectable in audit. The `min(val, test)` form itself penalizes val/test divergence, a first-order overfit signal.
- **What does NOT exist yet — stated plainly:** the runner does not *refuse* a mid-run rewrite. The fingerprint is logged, never compared: `composite.py`'s own docstring defers enforcement to "the runner checks the config hash against the original," and no such check is implemented. Additionally, a `custom_fn` callable is **outside the tamper-evidence envelope** — `fingerprint()` hashes the formula string and scalar params only, not the callable's source, so a callable-based metric can change without changing the fingerprint. Both fixes are a ~15-line patch specced in `not_vaporware.md` §5 (persist the campaign fingerprint at first run; compare per invocation; raise on mismatch absent a logged RULE_CHANGE; fold `hash(inspect.getsource(custom_fn))` into `fingerprint()`). Until it ships, the honest claim is **tamper-evident, not tamper-refusing** — ARCHITECTURE.md rule 9's "runner refuses" describes the design intent, not current code.
- **I/O:** in — per-fold metric values from `core/evaluation/metrics.py` (registry: AUROC, Sharpe, ARI, RMSE, …); out — one scalar + fingerprint string, appended to `experiment_log.jsonl`; runner verdict KEEP / DISCARD (NEAR-MISS exists as a reasoning-vocabulary verdict the agent can record, not a runner output — see dive 4 and D02's [planned] tag).
- **Key design choice:** *freeze the proxy cryptographically rather than trust the agent not to touch it.* Skalse et al. prove unhackable proxies don't exist [D30], so the design goal is not "Goodhart-proof" but "Goodhart-evident": any formula-string change alters the fingerprint and is visible in the ledger forever — and the refusal roadmap upgrades "visible" to "blocking."
- **Failure modes & fallbacks:** (a) the proxy can still diverge from the true objective under sustained optimization pressure [D31] — fallback: divergence monitor between composite and each raw target metric (ROADMAP, D08); (b) `min()` composites are noisy on small folds — fallback: NEAR-MISS re-evaluation routing (ROADMAP, D02); (c) fingerprint covers the formula string, not `custom_fn` callables (gap above, ROADMAP) and not the data — data hashing is gate 1's territory (dive 3).

## 2. Purge/embargo super-folds **[EXISTS]**

- **Goal:** make temporal/overlap leakage structurally impossible — scoped claim: the leakage classes split geometry can catch [D5][D8], not semantic leakage, not multiple-testing inflation.
- **Algorithmic approach:** López de Prado lineage [D6]–[D8]: `SuperFoldSplit` (`core/evaluation/splits.py:271`) takes pre-specified (val, test) windows, marks a `label_horizon_buffer` exclusion zone *before* each window (purge: drop training rows whose labels overlap the evaluation window; embargo: drop the serial-correlation buffer), and returns train = everything − union(val, test, buffers) as one "super-fold." Six sibling protocols (holdout, k-fold, stratified, group, time-series, walk-forward) share the interface; `validate_no_overlap()` asserts train∩val = train∩test = val∩test = ∅ on every fold and the runner refuses to launch on violation. `HoldoutSplit.min_train_idx` lets recency hypotheses drop old training rows *without touching val/test indices* — a small anti-reward-hacking affordance worth noticing.
- **I/O:** in — n_samples (+ y, groups where needed), window specs, buffer widths; out — `FoldAssignment` triples (train_idx, val_idx, test_idx, regime_label) consumed uniformly by the runner.
- **Key design choice:** *evaluation protocol as registry code, not as agent behavior.* The agent chooses *which* registered protocol fits the task (constitution §12 makes purge/embargo mandatory for temporal data); it cannot author a bespoke leaky split, because the runner only accepts registry protocols that pass the overlap assertion.
- **Failure modes & fallbacks:** (a) semantic leakage (illegitimate features, sampling bias — Kapoor–Narayanan types beyond geometry [D5]) passes untouched — fallback: data-integrity gate checks + human review of the feature list in the audit report; (b) mis-sized embargo under long-memory serial correlation — fallback: buffer width is a logged, cited config choice, challengeable in review; (c) one super-fold gives a point estimate, not a distribution — fallback: CPCV multi-path evaluation (dive 4, ROADMAP).

## 3. The three audit gates **[EXISTS — catch rates uncalibrated]**

- **Goal:** refuse to let an invalid experiment into the ledger — before compute is spent, not after.
- **Algorithmic approach:** two classes, deliberately distinguished (survey §4.4):
  **Deterministic gates** (strong evidence base): Gate 1 *data integrity* — programmatic split-overlap assertion (`validate_no_overlap()`, enforced at run time) **[EXISTS]**; GPU pre-flight is **[PARTIAL/ROADMAP]** — `gpu_memory_estimate_mb()` exists on every backbone but the runner never calls it, so today it is an available check, not an enforced one. Gate 2 *citation rigor* — `validate_citation_rigor()` (`core/reasoning.py`) rejects citations lacking any of six elements (authors, year, venue token, title/arXiv ID, relevance clause) and rejects placeholder sentinels; short-form "Keskar 2017" is rejected by construction **[EXISTS]**. Retrieval-verified citation checking is the one intervention shown to drive fabricated-reference rates (18–95% ungrounded, model/domain-dependent [D35][D36]) toward zero.
  **LLM-screen gates** (treated as screens, never guarantees [D33][D34]): Gate 3 *reasoning completeness* — `validate_reasoning_blob()` enforces word-count floors per field (diagnosis ≥60, hypothesis ≥50 with a mechanism/because clause, prediction ≥25, …) and required-keyword sets (verdict ∈ {KEEP, DISCARD, NEAR-MISS}) **[EXISTS]**. This is a structural completeness check on the artifact, not a validity judgment of the reasoning — the honest framing per positioning §4.5.
  **Enforcement point, stated with the bypass disclosed:** by default `core/runner.py` raises and refuses to launch if the pre-run annotation is missing or fails validation (`runner.py:220`, `runner.py:226`). There is one documented exception: `--bypass-reasoning-gate` (`runner.py:490`; checked at `runner.py:219`/`225`, documented in the repo's CLAUDE.md). It does **not** silently disable anything: the runner inserts `TODO-REWRITE` sentinels, tags the entry `_needs_rewrite`, marks the verdict "runner-fallback, rewrite manually" (`runner.py:392–395`), and the dashboard surfaces sentinel-tagged entries red. So the accurate statement is: *refusal by default; one visible, sentinel-tagged bypass; no silent path.* The earlier framing "refuses… / sentinel fallback" conflated the two paths — this is the reconciliation with the real code behavior.
- **I/O:** in — pre-run `ReasoningEntry` (7 fields) + split assignments + config; out — violation lists (empty = pass), launch/refuse decision, sentinel-flagged entries for human rewrite.
- **Key design choice:** *gate placement pre-commit AND pre-execution.* The gates run before compute is spent, so an invalid experiment costs a rejection message, not a wasted run — and the only ungated rows the ledger can contain are bypass rows, which arrive permanently sentinel-tagged and dashboard-flagged. This is what separates gates from post-hoc review, and it is the property the CMU failure-mode study says existing systems lack [A46].
- **Failure modes & fallbacks + calibration plan (ties to A11):** (a) regex-class citation checks verify *form*, not *existence* — fallback: live-index verification against OpenAlex/Semantic Scholar (free, commodity [B24][B25]) is the productization step; (b) word-count floors are gameable by verbose emptiness — acknowledged screen, backstopped by human spot-checks and (ROADMAP) cross-model LLM screens with known-bias caveats [D34]; (c) **catch rates are unmeasured** (survey §7). Calibration plan: seed known violations — planted temporal leakage, fabricated citations, prediction-free reasoning — into test campaigns; measure per-gate TP/FP rates; publish the confusion matrices and re-tune floors. Every calibration run's ledger feeds the private corpus (A11): gate catch-rate data on seeded violations is exactly the asset a fork of the open constitution cannot copy.

## 4. Trial-count-corrected acceptance gate **[ROADMAP — nobody has one, including the PoC]**

- **Goal:** make the keep/discard threshold rise with the number of trials actually run, so the 265th champion must clear a higher bar than the 5th — the deflated-composite analogue the survey says no published system implements (survey §6; the offensive move of positioning §4.6).
- **Algorithmic approach:** DSR/CPCV-based [D6][D7][D8]. (1) Maintain a **full trial ledger** — every experiment, kept *and discarded*, with seed, config, composite, timestamp (the PoC's `experiment_log.jsonl` already appends every run through the runner, so the raw ledger exists for runner-executed trials; a completeness audit of the historical ledgers is pending, and the correction that consumes the ledger is unbuilt). (2) At each keep decision, compute the expected max-of-N statistic under the null from the ledger's N and the observed variance (Bailey–López de Prado closed form for Sharpe; bootstrap/permutation analogue for generic metrics — the generic-metric null is a research task, flagged). (3) Accept only if the candidate clears champion + deflation margin. (4) For finance metrics, report DSR and PSR alongside raw; for distributional evidence, run CPCV multi-path evaluation on champion candidates only (compute-expensive, so triggered at acceptance, not per experiment — the laptop-budget compromise).
- **I/O:** in — full trial ledger (N, per-trial composites, trial variance), plus for the Sharpe closed form the **return skew, kurtosis, and track length T** of the candidate strategy [D6]; out — deflated acceptance threshold, DSR-annotated verdict, ledger-completeness attestation. **Scope of the attestation, stated precisely:** a hash chain over the ledger detects *post-hoc deletion or reordering* of rows — it cannot by itself prove no trial ran outside the ledger. Completeness against off-ledger trials rests on (i) sole-path execution — all experiments forced through the instrumented runner, ultimately a sandbox property in Sargsyan's sense [D32] **[ROADMAP]** — and (ii) external anchoring of the chain head (e.g., periodic publication of the running hash), so an omitted trial requires forging history that has already left the machine.
- **Key design choice:** *the ledger must include discards, and its completeness must be attestable.* A DSR computed on a cherry-picked ledger is theater. This is why the correction and the corpus (A11) are the same engineering: log every discard from day 1 — and route every trial through the one path that logs.
- **Failure modes & fallbacks:** (a) N is ambiguous when experiments are correlated (forking paths [D9]) — mitigations from the finance literature: effective-trial-count estimation via config-space clustering; conservative fallback is raw N; (b) generic-metric deflation lacks a closed form — fallback: permutation-null bootstrap, honestly labeled research risk; (c) a threshold that rises forever eventually freezes progress — fallback: threshold resets on regime-change or new-data events, logged as such.

## 5. Checkpoint/resume state machine **[EXISTS]**

- **Goal:** a multi-day research campaign on a machine that BSODs, sleeps, and thermal-throttles — resume with zero context loss from a file.
- **Algorithmic approach:** `CheckpointManager` (`core/checkpoint.py`) maintains one self-contained markdown checkpoint (`memory/project_autoresearch_checkpoint.md`) overwritten after **every experiment** and every **5 minutes of reasoning**, containing: champion snapshot (config + composite + per-fold table), last experiment, **exact next command to paste**, full history table, exhausted axes, and session-start instructions. Recovery contract: a *fresh* agent session reads only this file and continues (constitution §1: "Never assume state; verify it"). The state machine: IDLE → REASONING (5-min checkpoints) → GATED (audit gates) → RUNNING (fixed-duration) → ANALYZING → COMMIT/DISCARD → CHECKPOINT → IDLE; a crash at any state resumes at the last checkpoint's "next command."
- **I/O:** in — `ExperimentRecord` dataclass (record, champion, next_command + rationale, history, exhausted_axes); out — checkpoint markdown + append-only `experiment_summary.md`.
- **Key design choice:** *human-readable markdown as the durable state format, with the next action stored as a literal shell command.* No database, no daemon: the recovery path is "open new session, read file, paste command," which is also the audit path — the checkpoint doubles as a forensic record of what the agent intended next. Founder-reported: a multi-hour session survived a thermal shutdown and resumed with zero context loss (paper D.4).
- **Failure modes & fallbacks:** (a) crash *mid-experiment* loses at most one fixed-duration run (minutes) — acceptable by budget design; (b) checkpoint corruption on power loss mid-write — fallback: the JSONL ledger + summary reconstruct state (ROADMAP: atomic write-rename); (c) stale checkpoint after manual filesystem edits — constitution mandates verify-not-assume on resume.

## 6. BYOK model routing & cost control **[PARTIAL — PoC is single-assistant; routing layer is the product]**

- **Goal:** keep a 24/7 campaign's token bill at single-digit-to-tens of dollars per day (A12: tokens are user-side by construction; Pro margin carries no token COGS).
- **Algorithmic approach:** route by step class, not by loyalty (A9: LLM-agnostic by design; the PoC ran Claude-family agents — the constitution was written to behave consistently across assistants, paper App. A). Split at Aug 2026 list prices [B18][B19][B20]:
  | Step class | Loop steps | Tier | Example (in/out per Mtok) |
  |---|---|---|---|
  | Frontier reasoning | Diagnose, Hypothesize, stall self-reflection, constitution interpretation | Frontier/upper-mid | Sonnet 5 $2–3/$10–15; gpt-5.6-terra $2/$12 |
  | Routine execution | Execute scaffolding, log parsing, Document formatting, checkpoint writes | Mid/low | Haiku 4.5 $1/$5; Gemini 3.7 Flash $0.75/$3.75; gpt-5.6-luna $0.20/$1.20 |
  | Bulk retrieval | Literature-ground fetch/summarize (cacheable) | Low + caching/batch | cache hits at 10% of input price; batch −50% [B18] |
  Budget arithmetic (capability_table §3): ~2–5M fresh input + 0.5–1M output tokens/day with caching ⇒ $20–60/day all-Sonnet-tier, $3–12/day mid-tier-routed, <$2/day at the floor tier. Cost governor: per-campaign daily token budget; on breach, degrade gracefully (longer experiment intervals, cheaper tier for routine steps) rather than halt.
- **I/O:** in — user's API keys (BYOK), per-step-class routing table, daily budget; out — routed completions, per-step cost telemetry into the run record (D05), budget alerts to the dashboard.
- **Key design choice:** *the constitution is the portability layer.* Because behavior is pinned by a binding protocol file rather than by prompt idiosyncrasies of one vendor, swapping the model under a step class is a config change — the same property that de-risks platform dependence (A9) enables price arbitrage as the mid-tier gets 40–50x/yr cheaper per unit capability [B16][B17].
- **Failure modes & fallbacks:** (a) mid-tier models flub frontier-class steps — fallback: escalation rule (gate failure or self-assessed low confidence re-runs the step one tier up, logged); (b) frontier list prices rising [B19][B21] erodes the frontier slice — mitigation: the slice is small by design; (c) BYOK means Ascent can't see tokens for support/debugging — mitigation: local cost telemetry shipped in the run record, never the prompts (privacy posture, D06).

## 7. Stall detection + steering protocol **[PARTIAL — protocol exists in constitution §49–52; detector productization is roadmap]**

- **Goal:** keep the minimum viable human in the loop: detect when the campaign has stopped earning and convert one high-level sentence ("self-reflect on the stall") into a re-seeded search.
- **Algorithmic approach:** stall signal = no champion change in K experiments AND declining marginal composite delta AND exhausted-axes list growth (all three already logged per-experiment in the checkpoint/ledger). Response ladder (constitution §49–52, paper B.3): (1) agent self-reflection — re-run Diagnose against the *whole* history rather than the last champion; (2) literature sweep — search for a new backbone family rather than a tweak (re-seeding, the DeepEvolve escape from plateaus [D28][A4]); (3) surface a suggested steering prompt on the dashboard ("last three experiments show diminishing returns — consider researching new backbone families"); (4) human pivots ("pivot to new dataset", "research latest benchmarks"). Founder-reported ablation: high-level steering beat low-level intervention — low-level human edits *slowed* long-run convergence (paper C.2, single-seed); RE-bench independently supports the division of labor: agents win short bounded tasks, humans win long-horizon judgment [B4].
- **I/O:** in — ledger tail, champion history, exhausted axes; out — stall flag, ranked next-move suggestion, escalation prompt; human input is natural-language only.
- **Key design choice:** *steering is a logged, first-class event.* Every human prompt lands in `steering_log.md` — so the "minimum steering bandwidth" question the literature leaves open (survey §6) becomes measurable per campaign, and the steering log doubles as the demo (BRIEF: the log is proof that technical-lead-level humans can run research factories).
- **Failure modes & fallbacks:** (a) stall detector false-positives during legitimately slow high-variance phases — fallback: NEAR-MISS density in the window discounts the stall score; (b) self-reflection loops (agent "reflects" without changing strategy) — fallback: reflection must emit a *different* experiment-class than the last N, mechanically checked; (c) nobody watching the dashboard — fallback: notification channels (D10), and the honest limit stands: the paper concedes a human must notice the stall prompt.

## 8. Backbone registry & SOTA catalog **[PARTIAL — registry exists; catalog-as-subscription is roadmap]**

- **Goal:** give every campaign a literature-grounded starting grid — current SOTA architectures per task family — instead of the LLM's training-data prior.
- **Algorithmic approach:** `BACKBONE_REGISTRY` + `@register_backbone` decorator (`core/backbones/registry.py`); abstract `Backbone` contract (build/fit/predict_with_uncertainty/save/load/gpu_memory_estimate_mb — the memory estimate is defined for the GPU pre-flight check, whose runner-side wiring is [ROADMAP], dive 3). Shipped: MLP, LSTM, tabular transformer (PyTorch); XGBoost/LightGBM/CatBoost as **three separate registry entries** (deliberate: their SOTA recipes come from different papers and must not inherit each other's hyperparameters — ARCHITECTURE.md rule 6/7); `foundation_models.py` as the wiring stub for TimesFM/Chronos/MOMENT. Per-fork `sota_catalog.yaml` seeds task-specific grids — the Higgs fork's catalog held 14 modern tabular backbones (TabM, FT-Transformer, SAINT, MLP-PLR, …; founder-reported). Product form (ROADMAP): the catalog becomes a maintained, versioned subscription — task family → current SOTA entries with citation, reference config, and known-good recipe — curated from arXiv/S2 feeds (commodity retrieval [B24]) plus, on the paid tier, what-worked-where priors from the private corpus (A11).
- **I/O:** in — task type + registered backbones + catalog entries; out — `create_model(name, config)` instances, GPU pre-flight estimates, catalog citations that flow into Gate 2.
- **Key design choice:** *SOTA recipes are drawn from the originating paper, never inherited across backbones.* This is the anti-folklore rule: it forces the Literature-ground step to re-derive each baseline from its source, which is what makes "literature-grounded baselines" more than a slogan.
- **Failure modes & fallbacks:** (a) catalog staleness — versioned catalog with dated entries; the agent may propose additions, gated through citation rigor; (b) contaminated familiarity — the LLM may "know" a public benchmark's winning recipe [D37][D38]; mitigation: catalog provenance is explicit citations, and the clean test is private post-cutoff data; (c) registry sprawl — task_types filtering keeps the grid per-task finite.
